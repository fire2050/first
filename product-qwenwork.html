千问办公能力形态自评指南

面向准备接入千问办公的生态伙伴。本材料帮助你在正式对接之前，先自评自家产品/能力应该以哪种形态上架：专家套件（Plugin） / 技能（Skill） / 连接器（Connector）。选对形态可以显著缩短对接周期。

三种能力形态

千问办公面向"办公 Agent"场景，把外部生态能力抽象为三层，从下到上分别是：

01 · ROLE岗位级
全流程

专家套件 Plugin

多个 Skill + Connector + 岗位工作流封装

企业法务PE/VC 投资门店选址商家运营
组合
02 · TASK任务级
单一交付物

技能 Skill

一次完整任务的 Prompt + 工具编排 + 领域知识

docxOCR活动落地页履约诊断
依赖
03 · ATOMIC原子能力
数据 / 系统入口

连接器 Connector (MCP)

一组标准化 Tool（查询 / 读写 / 鉴权）

钉钉阿里云企查查北大法宝PolarDB

从底层数据入口，到单任务能力，再到岗位级完整工作流。

一句话辨别：

  • 你提供的是一组接口/数据源、让 Agent 能读能写你的系统 → 连接器

  • 你提供的是一次可交付的任务能力（分析报告 / 审查意见 / 决策清单）→ 技能

  • 你提供的是面向某个岗位人物、覆盖其 80% 日常工作的能力包 → 专家套件

三种形态详细对比

连接器 Connector

它是什么：一组符合 MCP（Model Context Protocol）标准的 Tool 集合。让千问办公里的任何 Agent 都能调用你的系统查询/读写数据。它不含 Prompt、不含工作流、不做业务判断——它就是"打通数据入口"。

典型形态（举例）：

  • 阿里云 CLI（查 ECS、开关机器）

  • 钉钉（读通讯录、发消息、创建审批）

  • Slack / Linear / Figma / Canva

核心特征：

维度 说明
交付物 一组 Tool（如 search_company、send_message），每个 Tool 描述清晰、参数标准化
使用者 Agent / Skill / Plugin 三者都可以调用
领域知识 不承载业务知识；只做接口暴露
触发方式 由 Agent 或 Skill 按需调用，不直接对用户
鉴权 目前支持标准OAuth鉴权，如果是API Key / Bearer Token等鉴权方式，需要单独沟通

你适合做连接器，当你符合以下 3 条中 ≥ 2 条：

  • 你的核心资产是数据/API/系统，且已经在为其它客户提供接口服务

  • 你希望别人（第三方 Skill 作者、企业内部 Agent）能基于你的能力自由拼装工作流

  • 你不想（或不擅长）写 Prompt 与领域工作流指令，只想把"能力"开放出去

技能 Skill

它是什么：一段告诉 Agent "遇到某类任务应该怎么做"的结构化指令 + 工具编排。核心是一份 SKILL.md（Frontmatter 描述触发条件 + Markdown 描述执行流程），可以搭配 references / templates / scripts等。Skill 承担业务逻辑，Connector 提供数据入口。

典型形态（举例）：

  • smart-image-reader / yescan-ocr-qoder：OCR 与图片理解

  • event-website：搭建活动落地页

核心特征：

维度 说明
交付物 一个 SKILL.md（+ 可选 references / templates / scripts等）
使用者 直接面向终端用户
领域知识 承载业务知识：什么时候用、按什么规则、输出什么格式、如何降级
触发方式 用户自然语言表达命中 description 中的关键词/场景，或者用户通过斜杠命令 / @ 提及选择技能
依赖能力 可以独立运行（内置知识 + LLM），也可以调用一个或多个 Connector 增强
粒度 一次完整任务：如"生成商家履约诊断报告"、"OCR 提取发票信息"、"生成活动落地页"

你适合做技能，当你符合以下 3 条中 ≥ 2 条：

  • 你有一个独立、可交付的任务场景（有明确输入、明确输出、明确判断规则）

  • 该场景不需要覆盖某个岗位的全流程，只解决一个具体问题

  • 你有明确的 Know-How（规则、模板、行业术语），希望封装成"最佳实践"发给用户

Skill 的边界（哪些不该做成 Skill）：

  • ❌ 单纯查一个数据 → 做成 Connector

  • ❌ 覆盖某岗位一整天的工作流（含决策 + 执行 + 汇报）→ 做成专家套件

  • ❌ 只是一个 Prompt 模板、没有工具编排、没有降级路径 → 建议改造成 Skill 或不上架

专家套件 Plugin

它是什么：一个可安装的 zip 包，内含多个 Skill + Connector + 岗位工作流封装。面向某个具体岗位人物，目标是覆盖其 80% 的真实工作场景。可以理解为"给某个岗位配一个 AI 助理"。

典型形态（举例）：

  • 企业法务专家（合规审查 + 类案检索 + 起草文书 + 电子签发起 + 法务日报 …）

  • PE/VC 投资专家（筛项目 + 尽调清单 + 审条款 + 投决备忘录 + 测收益 + 退出分析）

  • 商家运营专家（数据取数 + 活动推荐 + 履约诊断 + 复盘周报）

核心特征：

维度 说明
交付物 一个 zip 包，含 .qoder-plugin/plugin.json 清单 + skills/ 目录 + 可选 .mcp.json + commands/ + README.md + CONNECTORS.md
使用者 面向某个岗位角色；用户安装后即拥有该岗位的完整能力/大部分能力
领域知识 承载完整岗位工作流：一天/一周/一月怎么工作、每个环节用什么 Skill或者Connector
内部组成 一般≥ 3 个 Skill、1 组 Connector 声明、1 份 README、1 份连接器降级说明

你适合做专家套件，当你符合以下 3 条中 ≥ 2 条：

  • 你面向的用户角色明确且岗位化（法务、投资经理、商家运营、店长、门店选址人员……）

  • 你能列出该岗位一天/一周/一月的高频任务，且能拆成 ≥ 3 个独立 Skill

  • 你希望统一品牌打包（一次安装、一处入口、有独立的市场展示位）

三、快速自评：三个问题定位你的形态

按顺序回答，第一个"是"就是你的定位：

Q1：你要提供的核心价值是"打通一个数据源/系统"，让 Agent 能查能写吗？

  • 是 → 做连接器

  • 否 → 进入 Q2

Q2：你要提供的是"一次可完成的任务"（有明确输入、判断、输出）吗？该任务能不能用 1 个 Skill 交付？

  • 能，且不覆盖岗位全流程 → 做技能

  • 不能，需要多个任务串起来 → 进入 Q3

Q3：你要面向某个具体岗位人物（不是笼统的"用户"），并覆盖其 60% 日常工作吗？

  • 是 → 做专家套件

  • 否 → 拆回 Q2，先做单个 Skill

四、组合建议：三者不是互斥的

生态伙伴的常见路径：

  1. 只做连接器：适合数据源型公司（企查查、法宝等）。做完可以被别人的 Skill / Plugin 引用，同时自己也在市场露出。

  2. 只做技能：适合有单一垂直场景 Know-How 的公司（OCR、发票、活动落地页、履约诊断）。

  3. 连接器 + 技能：数据源公司想直接触达终端用户时，先建 Connector 打通接口，再写 Skill 教 Agent 怎么用你的接口做业务。

  4. 专家套件（自研 Skill + 引用他人 Connector）：垂直行业公司，掌握岗位工作流但不掌握所有底层数据。例如法务套件里引用官方"北大法宝"连接器。

  5. 专家套件（自研 Skill + 自研 Connector）：既有岗位 Know-How 又有系统数据的公司。最重的路径，也最完整。

五、开发投入参考

形态 主要工作量 上架周期（仅供参考） 需要的能力
连接器 实现 MCP Server（HTTP），标准化 Tool schema，OAuth/鉴权 如果已有，需要2天左右 后端工程 + OAuth 经验
技能 撝写 SKILL.md（触发条件、执行流程、输出格式、降级路径）+ 可选脚本/模板 如果已有，需要2天左右 业务专家 + 少量脚本能力

OAuth 鉴权要求

**none**（无需授权）——服务本身公开，或通过 URL 自带的凭据/网关侧校验完成鉴权。用户安装后即可直接使用，不会出现授权引导。

  • ✓ 适合公开数据类服务（搜索、词典、公开行业数据）

  • ❗ 不要用它承载「按用户区分数据权限」的场景——所有用户会共用同一身份

**oauth**（OAuth 授权）——每位用户各自授权、各自持有令牌，数据权限按用户隔离。用户首次使用时会被引导到你的授权页完成授权。

  • ✓ 需要区分用户身份、涉及私有数据的场景必须用这个

  • ❗ 你的授权服务器需完成下节的回调地址加白，否则授权必然失败

🚫 API Key 形式的鉴权目前不支持。 如果你的服务只提供 API Key 认证，请改为在服务侧包装成 OAuth，或改用 none + 网关侧凭据的方式，否则连接器在用户端会被标记为不可用。

OAuth 连接器必须完成的加白

QwenWork 客户端以标准 OAuth 授权码 + PKCE 流程发起授权。请在你的授权服务器上放行下面这些标识与回调地址，任何一项缺失都会在授权环节直接失败。

客户端标识（client_name / client_id）：

client_name = QwenWork
client_id   = qwenwork

  1. 若你的授权服务器支持动态客户端注册（DCR），客户端会自动注册，注册时提交的名称是 QwenWork。

  2. 若不支持 DCR，客户端会兜底使用固定的 client_id = qwenwork，请提前在你侧注册这个客户端。

  3. 客户端为公共客户端（public client），不持有 client_secret，请勿要求客户端凭据认证。

redirect_uri 白名单：

qwenwork-cn://mcp-oauth
https://nango.qwenwork.cn/oauth/callback
https://nango-cn-main-3uvzij.mulerun.cn/oauth/callback

  • ❗ 三个地址都要加白：第一个是桌面端直接回跳，后两个是 Web 端经授权代理网关回跳。

  • ❗ 必须精确匹配，不要做前缀匹配或通配。自定义协议 qwenwork-cn:// 也需要显式放行。

上架前的自查清单

检查项 要求
协议与可达性 HTTPS、公网可达、证书有效。不要依赖固定出口 IP 白名单
PKCE 需支持授权码 + PKCE（S256）
令牌刷新 建议下发 refresh_token 并支持刷新，否则用户需频繁重新授权。令牌过期时请返回 401，客户端会据此引导重新授权
工具描述质量 MCP 工具的 name 与 description 直接决定 Agent 会不会调用它。请写清用途、必填参数与返回内容，避免只写一个动词
幂等与超时 网络抖动时客户端会重连，但不会自动重放正在进行的工具调用。写操作请自行保证幂等，单次调用建议在数十秒内返回
错误信息 返回可读的错误摘要（哪个参数不对、缺什么权限），错误内容会直接影响 Agent 能否自行纠正重试。不要在错误里回显密钥或完整请求体

技能（Skill）接入开发指南

一个技能 = 一个目录 + 一份 SKILL.md。目录名就是技能的唯一标识，必须和你在表单里填写的名称字段完全一致。

硬性要求

要求 说明
技能zip包 ≤ 10 MB 仅 .zip，且包内条目数必须少于 1000
**<name>/SKILL.md** 包内必须存在这个精确路径，目录名要和填写的名称完全一致
名称只用小写 小写字母、数字、连字符，首尾不能是连字符，≤ 64 字符
图标 200×200 正好 200×200 像素、≤ 2 MB；SVG 免尺寸校验。见《附录：icon规范》

目录结构与打包

my-skill/                    ← 目录名 = 技能名称（如 contract-review）
├── SKILL.md                 # 必需，且路径必须是 my-skill/SKILL.md
├── references/              # 可选：长规则、行业知识，按需被读取
├── templates/               # 可选：输出模板
├── examples/                # 可选：示例
└── scripts/                 # 可选：脚本

打包命令（关键：要带上外层目录一起压缩）
  ✅  zip -r my-skill.zip my-skill/
  ❌  cd my-skill && zip -r ../my-skill.zip .      ← 少了外层目录，校验不通过

🚫 最高频的失败原因： 压缩包里找不到 <名称>/SKILL.md。校验是精确路径匹配——如果你在 macOS Finder 里选中目录内的文件再右键压缩，得到的包是 SKILL.md 而不是 my-skill/SKILL.md，会被直接拒绝。请务必压缩整个目录。另外目录名和表单里的名称必须一字不差（大小写敏感）。

专家套件（Plugin）接入开发指南

千问办公"专家套件（Plugin）"是生态伙伴与千问办公联合交付的、可安装的岗位级 AI 能力包。它以覆盖目标用户 60% 的真实工作场景为验收标准，由生态伙伴贡献行业 Know-How（Skill 编写 + 部分 Connector 提供），千问办公侧负责平台能力支持与集成验收。

专家套件的四条核心原则

原则一：场景先行，MCP 后补

必须从目标用户的一天、一周、一个业务周期出发，而不是从客户现有系统能力出发。正确路径是：

先定义目标用户和业务结果 → 再盘点高频工作场景 → 再判断哪些场景适合 AI 代理化 → 最后确认需要哪些 MCP 能力支撑。

验收红线：如果某个高频场景因为暂时没有接口或 MCP 就被删除，是不合格的。正确做法是保留场景，标注"能力待接入"或"首期降级处理"，再决定是否进入 MVP。

原则二：专家套件解决完整任务，不包装功能点

一个 Skill 应对应用户可感知的一次完整任务，而不是一个 API 调用。

好的 Skill 粒度：分析本周店铺经营异常并生成行动建议；识别高风险订单并生成处理清单；根据评论、售后和客服记录提炼商品改进建议；汇总供应商报价，生成采购比价表和推荐理由；根据合同条款和历史案例生成风险审阅意见。

不好的 Skill 粒度：查询订单 API、读取评论数据、调用商品详情接口、导出 Excel、生成一段通用文案。

原则三：聚焦高频、长链路、带 Know-How 的任务

专家套件不是把客户系统搬进千问办公，而是优先选择千问办公最能放大的任务：高频（用户经常做，节省时间能被明显感知）、长链路（跨多个系统/文件/表格/消息/网页完成）、有判断（需要规则、经验、排序、取舍）、有交付物（能输出报告、清单、文档、表格、文案等）。

原则四：写操作必须有确认门，异常必须可恢复

涉及写入、发送、提交、下单、改价、发布、退款、审批、对外通知等动作时，必须有用户确认门。MCP 不可用、鉴权失败、数据缺失、权限不足、接口超时时，Skill 需要提供降级路径，而不是直接中断。

方案提报

目标：生态伙伴产出一份可评审的《专家套件方案书》，让千问办公能判断"这个套件值不值得投入审核和联调资源"。

方案书必须回答四个问题：

  1. 服务谁：目标角色人物（Persona），包括岗位、组织规模、常用工具、KPI、痛点。写"服装电商 3–50 人团队的运营负责人"，而不是写"电商用户"。

  2. 他们怎么工作：目标用户的一天/一周/一月工作流。每个环节标注：输入、判断、输出、频次、当前耗时、当前痛点。这一步是全流程的地基——不写清工作流，后面所有 Skill 都是空中楼阁。

  3. 对应什么能力：把工作流映射到 Skills 和 Connectors。

    • Skills：一个 Skill 对应用户可感知的一次完整任务

    • Connectors：每个 Skill 需要哪些外部数据/系统，是否有 MCP 或需要新开发。

  4. MVP 范围：圈定首期落地的 3–8 个核心 Skill。

方案书模板结构清单
Persona 画像

用一段话描述目标用户，避免泛人群。示例：

"服装电商 3–50 人团队的运营负责人，日常需要盯直播、盯投放、盯库存，每周产出经营复盘周报给老板。"

需要包含：岗位、组织规模、日常主要工作、最终交付物、成功指标（例如提效 / 增收 / 降本 / 风险下降）。

场景清单，按用户任务切分

以表格形式列出目标用户的高频场景清单，按用户任务而非接口模块切分。每个场景填写：

场景名 频次 当前痛点 输入 期望输出 是否有写操作/敏感数据

红线：不因"暂时没接口"就删掉高频场景，标注"能力待接入 / 首期降级"即可。

套件的构成：Skills + Connectors

将场景映射为一个专家套件，包含：

  • 3 个以上核心 Skills：每个 Skill 对应用户可感知的一次完整任务。列出 Skill 名称、触发场景、输入、输出。

  • Connectors 清单：自研 MCP / 需要千问办公提供 / 第三方各类分别列明；每个 Connector 说明鉴权方式、权限范围、租户边界。

  • 降级方案：无 Connector 时该 Skill 如何独立运行。

  • 风险动作确认门：涉及写入、外发、财务的动作，说明如何设计人工确认环节。

以上三部分即为方案书的核心内容。审核通过后进入下一步。

人工审核

目标：千问办公侧从场景真实性、技术可行性、安全合规三个维度对方案书做人工审核，通过后才进入开发。

审核维度 关注点
场景真实性 是否按用户任务而非接口模块切分；是否高频、长链路、带 Know-How；是否有客户/数据支撑（不是拍脑袋想的伪场景）
技术可行性 Skill 粒度是否合理；Connectors 是否有明确接入路径；是否会陷入"没接口就不能用"的死循环
安全合规 是否有写操作/外发/财务动作；是否有确认门设计；敏感数据处理是否合规；租户/权限边界是否清晰
商业价值 是否与商务沟通阶段的商业模式一致；试点客户是否落实

审核结论有三种：

  • 通过：进入开发。

  • 修改后通过：针对特定问题（如 Skill 粒度过细、缺少降级方案）迭代后再审。

  • 驳回：场景不成立或商业价值不足，重新收敛。

# 竞品调研简报（测试技能）

> ⚠️ 本技能属于测试套件，用于验证「多步骤 + 参考文档」的技能形态。输出仅供流程演示，不构成任何投资或经营建议。

## 适用场景

用户想快速了解某个赛道 3–5 家主要玩家的对比，用于内部立项、路演材料或产品迭代方向讨论。

## 执行步骤

1. **确认范围。** 若用户只给了行业关键词，先列出候选 5 家竞品让用户选择/追加；若用户已给出名单，直接进入下一步。
2. **信息采集。**
   - 若 `test-knowledge-base` 已连接：调用其检索工具拉取内部资料。
   - 若未连接：通过公开来源（官网、公开新闻）逐家搜集，标注信息来源与日期。
3. **维度对齐。** 强制按以下五个维度整理，缺失字段标注「未公开」而非留空：
   - 定位一句话
   - 主要用户/客户
   - 定价模式（免费/订阅/项目制/…）
   - 差异化卖点
   - 主要销售渠道
4. **生成对比表。** 用 Markdown 表格呈现，每家竞品一行。
5. **SWOT 快评。** 对每家竞品各写一行「优势 / 劣势 / 机会 / 威胁」，每项 ≤ 30 字。
6. **给出行动建议。** 面向使用本技能的团队，给出 3 条差异化定位建议，每条附一句判断依据。

## 输出格式

```
# 竞品对比简报：<行业 / 主题>

## 一、竞品对比表
| 竞品 | 定位 | 用户 | 定价 | 差异化 | 渠道 |
|------|------|------|------|--------|------|
| ...  | ...  | ...  | ...  | ...    | ...  |

## 二、SWOT 快评
### 竞品 A
- 优势：...
- 劣势：...
- 机会：...
- 威胁：...

## 三、我方差异化建议
1. ... —— 依据：...
2. ... —— 依据：...
3. ... —— 依据：...

## 信息来源
- 竞品 A：<链接> · <日期>
- 竞品 B：...
```

## 未连接连接器时的降级

`test-knowledge-base` 未连接时，不要虚构内部资料。改为要求用户粘贴现有材料，或明确告知只能基于公开信息作答。
套件内.mcp.json规范

如果套件内的技能需要读写外部系统，在包根目录放一个 .mcp.json，键名就是连接器的 Server Key。解析时会把每个键识别成一个依赖的连接器。

{
  "mcpServers": {
    "figma": {                       -- 套件内依赖的连接器server key，连接器上架时的字段，如果需要可联系官方
      "type":"http",                 -- 依赖的连接器服务协议类型
      "url":"https://xx.xxx.com/mcp" -- 依赖的连接器服务地址
    },
    "my-crm": {
      "type":"http",
      "url":"https://xx.xxx.com/mcp"
    }
  }
}

💡 这里声明的连接器必须是已经上架的连接器的 Server Key。键名写错不会报错，但用户安装套件后会看到一个连不上的数据连接项。另外在提交表单里还有一个**「引用连接器」**多选框——在那里勾选的连接器会随套件一起安装，并复用用户已有的授权，不需要重新授权一次。

附录：icon规范

图标是可选的，不上传会使用兜底图标。但一旦上传，下面三条全部必须满足，缺一不可。

项 规则 说明
尺寸 正好 200 × 200 像素 是等式校验，不是上限也不是建议值。512×512、200×201、199×199 均会被拒绝，提示「图标尺寸需为 200x200」。SVG 免尺寸校验——矢量图可以不是 200×200
大小 ≤ 2 MB 200×200 的图正常不会超过几十 KB。如果你的文件接近 2 MB，很可能是 GIF 帧数过多或 SVG 内嵌了位图
格式 8 种图片格式 PNG、JPG/JPEG、SVG、WebP、GIF、BMP、ICO。校验依据的是文件的真实类型，不是改扩展名就能通过。把 .heic 改名成 .png 会报「不支持的图标格式」

💡 除了上传文件，也可以直接填写一个已有的图片 URL（≤ 1024 字符）。如果采用外链，请确保该地址长期可用且允许跨域引用，否则用户侧会看到碎图。
